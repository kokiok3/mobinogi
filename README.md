# 모비노기
## 후다🐔 보는 웹사이트

</br>


## 💬 프로젝트 소개
**서비스 요약**  
마비노기 모바일의 서버 통합 랭킹을 한눈에 볼 수 있습니다. 전투력, 매력, 생활, 종합 랭킹의 TOP 500 유저 정보를 제공하는 웹 서비스입니다.

**기획배경**  
마비노기 모바일 공식 홈페이지는 서버별 랭킹만 제공하여 전체 순위 파악이 어렵다는 불편함이 있었습니다. 이를 해결하기 위해 모든 서버의 데이터를 통합하여 Top 1,000 통합 랭킹을 한눈에 볼 수 있는 서비스를 기획했습니다.  
이미 유사한 서비스들이 존재하지만, 풀스택 프로젝트를 직접 설계하고 배포하는 과정을 통해 기술적 숙련도를 높이는 것을 목표로 했습니다. 특히 SSR 기반의 Next.js를 익히고, 공식 사이트의 봇 감지 시스템을 고려하여 최대한 실제 사용자의 브라우징 동작을 모사하는 크롤링 전략을 구축했습니다. 

</br>


## ✨ 주요 기능
-  **서버 통합 랭킹 조회** - 주기적 데이터 수집(Cron) : node-cron을 활용하여 [시간]마다 공식 사이트를 크롤링하여 최신성 유지했습니다.

## 🔥 기술적 도전 과제
* **SEO:**
  Next.js를 도입한 주요 목적은 사용자 유입을 위한 SEO였습니다. 사용자 유입이 중요한 서비스 특성상 검색 엔진 노출을 높이는 것이 핵심과제라고 판단했습니다.
  * 기본 HTML에 포함되는 정보가 제한적인 점을 보완하고자, meta 태그에 최대한 다양한 연관 데이터를 추가하는 방식으로 SEO를 시도했습니다.
  * 공식 홈페이지와 유사한 랭킹 서비스의 페이지 소스를 분석하여 어떤 메타 정보가 구성되어 있는지 확인하고 이를 반영했습니다.
    
* **인간 친화적 크롤링 전략:**
  공식 사이트의 봇 감지 시스템을 우회하고 수집 안정성을 확보하기 위해 다음 전략을 도입했습니다.
  * 랜덤 대기 시간: 일정한 수집 패턴을 피하려고 요청 간 랜덤 지연 시간을 적용하여 실제 유저의 동작을 모사했습니다.
  * 성능 최적화: Got 라이브러리를 통해 HTTP/2를 지원했으며, 쿠키 수집 시 사용하는 브라우저 실행의 리소스 소모를 최적화하는 데 집중했습니다.
  * [User-Agent & Cookie 관리]: 브라우저 정보를 매번 다르게 설정하고 서버별 쿠키를 동적으로 수집하여 차단을 방지했습니다.
    
* **모노레포**: npm workspaces를 활용해 클라이언트(랭킹 조회), 서버(크론, 크롤링, 데이터 저장), 공유 타입을 하나의 저장소에서 관리하며 코드 중복을 최소화했습니다.
  * CJS 기반의 Node환경과 ESM 기반의 프론트엔드 환경을 통합하기 위해 tsconfig와 package.json의 moduleResolution 및 rootDir/outDir경로를 세밀하게 설정하여 파일 참조 오류와 빌드 시 경로문제를 해결했습니다.
    
* **Docker**:
  * 조회성 명령어를 이용한 디버깅 위주로만 경험이 있었는데 DockerFile, Docker-compose.yml를 직접 설계하며 서비스 구동에 필요한 런타임 환경을 코드화하는 경험을 했습니다.
  * DockerFile를 기반으로 배포를 하는 Railway에 배포 전에 Docker Desktop을 활용해 사전 검증함으로써 배포 실패율을 낮추고 디버깅 효율을 높였습니다.
    
* **Redis**: 반복적인 크롤링 요청을 방지하고 빠른 검색 결과를 제공하기 위해 Redis에 캐싱하여 API 응답 속도를 극대화했습니다.
  
* **인프라 적용**: 스케줄링(Cron) 작업이 필요한 서비스 특성 상, Stateless(요청이 있을 때만 구동되는 서버 전략)한 Vercel의 한계를 인지하고 상시 구동형 PaaS인 Railway를 도입하여 [시간]주기 데이터 파이프라인을 안정적으로 구축했습니다.

## 🌊 개발자 회고  
* **SEO:**
  공식 홈페이지가 다양한 검색어에도 상위에 노출되는 것을 확인하며, 보유한 데이터의 양이 SEO에 중요한 영향을 준다는 점을 체감했습니다.
  연관 검색어를 기준으로 검색 결과 내 노출 순위를 확인하고, 메타데이터를 보완할 때마다 순위 변화를 관찰하는 과정이 재밌었습니다. SEO개선 효과를 직접 확인할 수 있었습니다.
  
* **Tailwind CSS**: 적용이 쉽지만 스타일이 많아질 수 록 유지보수하기 까다로웠습니다. 클래스명 코드가 길어져 가독성이 떨어진다고 생각되어 개인적으로 선호하는 방법은 아니었습니다. 차라리 CSS-in-JS 가 JS 유저에게 더 다루기 쉬운 선택지로 느껴졌습니다.
  
* **데이터 수집의 한계**: 넥슨에서 제공하는 오픈 API가 있을 거라 생각했는데 제공되는 오픈 API가 없어서 크롤링을 하게 되었습니다. 공식 홈페이지에서 데이터 요청 시 데이터 리스트가 아닌 HTML을 응답으로 주기 때문에 HTML 기반으로 크롤링해야 했는데 DOM 구조 변화에 취약한 점이 아쉬웠습니다. 이에 따라 전체 유저 조회를 하기에는 부담이 커서 서버 부하를 최소화할 수 있도록 카테고리별 상위 ~~1000~~ 500명으로 제한했습니다.
  처음에는 got을 이용해 http2 호환이 가능한 통신 라이브러리를 사용했습니다만 로컬, Docker desktop 환경에서만 통신이 되고 Railway에 배포를 한 뒤에는 통신이 되지 않는 문제가 있었습니다. 이는 Railway에서 아웃바운드 설정이 되어 있어있지 않아서 통신이 이뤄지지 않았기 때문입니다. 이를 간단히 해결하기 위해 got라이브러리 대신 이전에 쿠키수집을 위해 사용한 puppeteer를 이용해 크롤링을 수행하기로 했습니다. puppeteer를 사용하면 브라우저를 이용해 데이터를 수집하기 때문에 통신문제는 해결되었습니다. 하지만 Cloudflare를 통해 봇으로 인지되었습니다. puppeteer에서 Cloudflare를 우회하는 puppeteer-real-browser 라이브러리가 있다고 합니다. 리눅스 시스템에서 사용할 경우 xvfb도 설치가 필요합니다. (puppeteer-real-browser 는 시도하지 않았습니다.)
  
   결국 Docker desktop에서 크롤링한 데이터를 배포한 Redis에 데이터를 저장하는 방식으로 진행했습니다. 하지만 1,000개 이상의 데이터를 수집하는 데는 여전히 어려움이 있었습니다. 아래는 시도한 2가지 방법입니다.

  1. 랜덤 대기시간: 대기시간으로  500/13000 ~ 30000(최소/최대ms)를 시도했습니다. 최대를 30초로 설정했을 때는 안정적으로 원하는 데이터를 모두 수집했습니다. 하지만 하나의 카테고리 소요시간이 약 20분이나 걸렸습니다. 4개의 카테고리를 모두 수집하려면 1시간을 훌쩍 넘었습니다. 최대 15초로 설정했을 때는 한 카테고리당 약 10분 이상 소요했습니다. 여기까지의 작업은 모두 got라이브러리를 사용했을 때 입니다. puppeteer를 이용한 크롤링 시에는 병렬 실행을 시도했습니다. 왜냐하면, 각각 독립된 브라우저 컨텍스트를 가지고 쿠키와 같은 저장소 또한 독립된 환경을 가지기 때문에 크롤링 시간을 절약할 수 있기 때문입니다. 500/13000(최소/최대ms)을 시도했을 때 모든 카테고리의 약 600개 데이터 수집이 약 10분 소요되었습니다.
  2. User-Agent 변경: Request Header의 User-agent 를 특정 주기마다 바꿔주어 다양한 환경에서 접속하는 듯한 흉내를 냈습니다. 하지만 User-agent를 추가하니 오히려 봇 감지 시스템에 쉽게 걸렸습니다. User-agent를 사용하면 사용 기기 사이즈와 호환 브라우저 맞추는 등 좀 더 섬세한 컨트롤이 필요한 것 같아 차라리 제거했습니다.

  위 2개의 시도로 1,000개의 데이터를 크롤링하려고 했지만, 실제 공식 서비스에서도 반복적인 물리적 접근을 막기 때문에 크롤링이 어려웠습니다. 또한 분 단위로 변경되는 데이터를 10분 이상 크롤링하는 것은 공식 사이트와의 데이터 정합성이 많이 떨어질 것같아 크롤링이 안정적으로 수행되는 500개로 제한했습니다. 데이터 수집의 한계를 보완할 방법을 알아보았을 때 프록시를 이용해 ip를 지속적해서 바꿔주는 등의 방법도 있다고 합니다. 이번 프로젝트에서는 성공적인 크롤링이 목표라기보단 풀스택 프로젝트를 직접 설계하고 배포하는 과정을 통해 기술적 숙련도를 높이는 것을 목표로 했기 때문에 크롤링은 puppeteer를 이용해 500개만 수집하는 것으로 마무리했습니다. 이번 프로젝트를 통해 실제 상용하는 랭킹 서비스를 제공하지 못하게 된 점이 아쉽고 크롤링을 하기 위해서 생각보다 많은 우회가 필요하다는 것을 배웠습니다.

* **백엔드 아키텍처 설계에 대한 고찰**: 기존 코드의 유지보수가 아닌, 백엔드 아키텍처를 밑바닥부터 설계했습니다. 확장성을 고려한 API 리스폰스 포맷을 위해 객체화하려고 했지만, 구현 지식에 부족함을 느꼈습니다. API 서비스 로직이 상대적으로 적어 당장 구현을 위주로 코드 작성을 했지만, 앞으로 보완해 나가야 할 과제라고 생각합니다.
